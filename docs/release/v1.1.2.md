# Server 1.1.2

Database schema 33. Client contract 1.1.0 and wire 3 (wire 1/2 retained).
The additive Admin API and contract-bundle edition is 1.1.1; existing SDK pins
and client discovery remain compatible without an SDK update.

## Changes

OpenRouter error responses now receive bounded parsing with an absolute
deadline. Only allowlisted categories, structural parameter paths, provider codes
and correlation IDs survive; raw messages, bodies, prompts and secrets do not.
Parsing is selected only for the protected HTTPS OpenRouter endpoint, not from
client headers or an arbitrary OpenAI-compatible provider.

A complete, unambiguous HTTP 400 request-validation error can establish a
pre-generation rejection. Such attempts release input/output/total-token and
cost reservations, but still count logical requests and upstream attempts.
Rejection never fabricates provider-reported token counts or a zero-dollar bill.
Untyped errors, truncated responses, timeouts and ambiguous failures retain the
conservative policy. Validated reported usage can settle new failed attempts;
the versioned evidence preserves historical settlement semantics on replay.

The Admin API, CLI and Console expose optional usage details that distinguish
reported measurements, unknown conservative charges, and missing values. They
also accept the valid denied-quota-rule/denied-reservation decision sequence
instead of producing an internal error. Confirmed provider request rejection
returns the existing non-retryable `request_invalid` client error; operators can
inspect safe provider diagnostics through the Admin API.

Input bounds now expose their aggregate rewritten bytes, framing units,
per-request/per-unit framing, and expanded schema bytes. Simulation includes
the schema expansion term. This release does **not** claim exact tokenizer
accuracy or lower hard-quota bounds using an unvalidated estimate.

## Deployment and recovery

Back up the database and existing Compose configuration before migration.
Pin the published `ghcr.io/latchway/latchway:1.1.2` image by its verified digest
for both the migration and gateway services; run migrations before serving.
Migrations 32/33 are additive and leave existing attempts unchanged.

After upgrading, unmodified schema-31 images cannot pass the exact-schema
readiness check. Recovery must use a tested schema-33-compatible image, or a
pre-upgrade database backup restored into a separate database with its matching
image. Do not drop diagnostic records or rewrite the migration ledger to force
an image downgrade. Keep the original database for forensic recovery.

Historical unknown charges are not automatically refunded: they still require
provider evidence and an auditable operator correction. Prompt logging remains
off by default. No cloud, Android device or Apple extension evidence is inferred
from the local regression suite or deployment.
