# Server 1.1.3

Database schema 33 is unchanged. Client contract 1.1.0 and wire 3 remain
compatible; wire 1/2 stay supported. The additive Admin/configuration bundle
edition is 1.1.2. Published older bundles and SDK contract locks are not replaced.

## Development attestation

`appAttest.environment` accepts `development`, `production`, or `any`. The `any`
policy accepts either cryptographically verified Apple environment so a
Development backend can support local builds and TestFlight. It is a server
policy, never an Apple entitlement or a stored key environment. Actual key
environments, app identity, challenge binding, signatures and counters remain
verified. Signing/distribution categories remain a separate allowlist. New
Development Console setups default to `any` with local-signing/TestFlight
categories; existing environments are not changed automatically. Accepting
development evidence in Production requires explicit audited acknowledgment.

Google Play Console test responses can be explicitly accepted only by a
Development policy using `allowTestingResponses: true`. They retain `debug`
trust through session exchange, renewal and feature authorization. Package,
certificate, binding, freshness, licensing and configured verdict checks remain.
The normal minimum trust setting and global trust ordering are unchanged;
Staging and Production cannot enable this exception. This is not a universal
debug-APK bypass and requires matching Google tester/app configuration.

After any configuration revision changes, App Attest and Play Integrity grants
require fresh attestation before renewal. This deliberately avoids inferring
provider facts from older grants, including after unrelated policy edits. Native
and React Native shared roots use the same server-owned policy. Direct delegated
step-up remains Apple-only, and a child cannot elevate a simulated parent's trust.

## Security maintenance

Google service-account OAuth assertions/exchange and metadata access use Google's
maintained Go libraries behind fixed endpoint, scope, bounded-response and
redaction boundaries. Security JSON parsing uses the standard Go decoder while
retaining exact numbers, duplicate/UTF-8 checks and size/depth/node limits. Shared
strict P-256 coordinate decoding and the existing JWT library replace duplicated
ES256 verification plumbing; no additional JOSE dependency or key format change.

## Deployment and rollback

Pin `ghcr.io/latchway/latchway:1.1.3` to its verified published digest for the
gateway and migration service. Existing schema-33 deployments need no additional
SQL migration; the migration service remains the idempotent schema check.

Upgrade the server before activating `any` or Google testing acceptance. Before
rolling back to 1.1.2, restore singular Apple acceptance policies and disable
Google testing responses. Do not change Production as a workaround for failed
development verification. Identity, quotas, secrets and existing tenant policy
documents are unchanged by publishing this image.

Automated cryptographic fixtures and local PostgreSQL/Console checks are not
physical-device, TestFlight or live Google-verdict evidence. Those checks remain
separate from package publication and server rollout.
