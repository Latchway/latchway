# Latchway server 1.0.3

This patch lets native and React Native clients share an application's signed
platform identity while keeping separate, directly attested component roots.

## Changes

- An `ios` / `react_native_ios` main-app root pair can share a bundle identifier
  when both use direct App Attest.
- An `android` / `react_native_android` app-root pair can share a package name
  when both use direct Play Integrity.
- Configuration validation and runtime loading apply the same narrow exception.
  Root selection still matches the exact platform and attestation provider.
- Same-platform duplicates, third roots, delegated overlaps, wrong component
  kinds/providers and mismatched attested identities remain rejected.

No client API, identity policy, attestation verification, route or quota behavior
changes. Separate roots do not create separate quotas unless the configured
quota scope explicitly does so. Existing SDK releases work without a native
SDK upgrade; React Native 1.1.2 also includes an independent URL-bootstrap fix.

## Image and upgrade

```text
ghcr.io/latchway/latchway:1.0.3
```

Linux amd64 and arm64 are published together; `1.0`, `1`, and `latest` are moving
aliases. Pin the published digest for reproducible deployments and use the same
image for server and migrator. Contract 1.0.0, wire 2 with compatible legacy
wire 1, and database schema 29 are unchanged. No new migration is required.
Keep the database URL, encryption master key and public origin unchanged.

Upgrade the server before activating a shared-identity configuration. When
rolling back to public 1.0.2 or earlier, first activate compatible revisions
without shared native/RN identifiers in every affected environment. The old
runtime cannot load the new definitions. No database rollback is needed.

## Verification boundary

The complete Go package suite passes, including semantic/runtime positive and
negative shared-root regressions. The compatible private VPS build passed
configuration validation, allow/deny simulations and readiness for native/RN
iOS and Android. Those are configuration/deployment checks, not a real Habitify
device proof or evidence against this exact public image. Android physical
Play-distribution, production Apple distribution, extension, cloud-matrix,
independent-review and load certification remain separate work.
