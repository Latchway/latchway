An environment has one active immutable configuration revision. Editing never
mutates that revision in place: Latchway creates a draft, replaces its complete
document under a strong ETag, validates it, produces a redacted plan, and then
atomically activates it.

## Configuration shape

Every document uses the following envelope:

```json
{
  "apiVersion": "latchway.dev/v1alpha1",
  "kind": "EnvironmentConfig",
  "metadata": {
    "organization": "example",
    "application": "mobile-app",
    "environment": "production"
  },
  "spec": {
    "identityProviders": [],
    "attestationPolicies": [],
    "upstreams": [],
    "models": [],
    "inputAccountingProfiles": [],
    "pricingCatalogs": [],
    "limitPlans": [],
    "features": [],
    "session": {},
    "privacy": {}
  }
}
```

The required `spec` collections connect in this direction:

```text
identity provider + attestation policy
                 |
managed secret -> upstream -> physical model
                              |       |
                input accounting   pricing
                              \       /
                       feature routes
                              |
                         limit plan
```

References are stable logical IDs. A feature protocol must agree with the
selected model capability, an upstream authentication reference must resolve
to a current secret, and hard input, total-token, or input-priced cost rules
must have model-aware accounting and pricing that the server can prove.

## Setup wizard

The current embedded wizard generates a production-native template with
Firebase Authentication, required App Attest and Play Integrity, and an OpenAI
Responses feature. Use it only when those exact production inputs are
available:

1. Create the organization, application, and environment.
2. Add the application's Firebase project.
3. Add the exact App Attest and Play Integrity production identifiers.
4. Store the upstream credential as a write-only secret.
5. Configure upstream, physical model, input accounting, pricing, feature,
   routes, and limit plan.
6. Validate and inspect the structural plan.
7. Simulate representative platforms, claims, trust levels, and request bounds.
8. Activate and copy the generated SDK application resource ID and environment.

The generated `app_...` application ID is not a display name, bundle ID,
Android package name, or slug.

Other supported identity providers, web attestation, protocol adapters, and
signed debug policies are configured through the dedicated resource editors,
full configuration editor, CLI, or Admin API. The isolated `verify local`
command owns the supported turnkey debug path; the production wizard does not
offer a debug switch.

### Opaque HTTP path templates

New opaque features use exact-depth provider-relative templates:

```json
{
  "opaqueHttp": {
    "allowedMethods": ["GET", "POST"],
    "pathTemplates": [
      "/v1/health",
      "/v1/accounts/{account_id}/status"
    ],
    "maxBodyBytes": 1048576,
    "allowedRequestHeaders": ["Content-Type", "X-Trace"]
  }
}
```

A capture matches one complete canonical segment and never changes the
configured upstream authority. Templates must not overlap and cannot contain
catch-alls, partial captures, traversal, encoded separators, queries, or
absolute destinations. Existing `pathPrefixes` configurations retain their v1
segment-bound behavior, but a policy cannot combine prefixes and templates.

## CLI workflow

Pull the redaction-safe active document and use it as a reviewed starting point:

```bash
latchway --output json config pull --environment env_... > active.json
latchway config apply --environment env_... --file candidate.json --dry-run
latchway config apply --environment env_... --file candidate.json
```

A normal apply creates the draft, validates it, plans against the active base,
and activates with the newest ETag. To guard explicitly against a stale base:

```bash
latchway config apply \
  --environment env_... \
  --base-revision rev_... \
  --file candidate.json
```

Individual lifecycle commands are available when a review process separates
the stages:

```bash
latchway config validate rev_...
latchway config plan rev_...
latchway config diff rev_...
latchway routes simulate rev_... \
  --feature assistant \
  --platform react_native_ios \
  --trust-level app_verified \
  --claims-file normalized-claims.json
latchway config rollback rev_... --environment env_...
```

Simulation runs the exact compiled policy and route resolver without reserving
quota or dispatching upstream traffic. Claims come from a bounded regular JSON
file so they do not enter shell history.

A simulation can also make routes fail (`failures` in the request, `--fail` in
the CLI) and returns the attempt plan the data plane would follow, using the
same retry and fallback decisions. `POST /config-revisions/{id}/simulate-batch`
runs up to 50 simulations at once, and an application can keep named
simulation scenarios (`/applications/{id}/simulation-scenarios`) that the
team reuses.

To see who a limit would stop before publishing it,
`GET /admin/v1/usage/distribution` sums one metric per user (or per user and
feature, or installation) in each calendar window of the limit, aligned the way
enforcement aligns them, and reports peak percentiles, a histogram, and how
many users would have exceeded a maximum, without returning user IDs.
`GET /admin/v1/user-overrides` lists active and ended plan overrides, and a
user's effective configuration includes each limit's current usage.

## Drafts

A draft stays editable until it is activated, including after it validates;
editing returns it to `draft`, so it needs validating again before activation.
Every create and edit is recorded with its author, time and changed paths
(never values):

```bash
latchway config history rev_...
latchway config apply --environment env_... --file candidate.json \
  --note "Raise the free plan to 50k tokens"
latchway config discard rev_...
latchway config promote --environment env_production --from env_staging
```

`--note` records a publish note on the activated revision. Discarding sets a
never-activated draft aside: it stays in history as `discarded` and can't be
edited, validated, simulated or activated. Activated revisions can't be
discarded or changed.

A draft records the live revision it started from. If something else is
published first, the draft can't be activated until it is brought up to date:
`GET /admin/v1/config-revisions/{id}/rebase-preview` lists, by path, what each
side changed and where both changed the same thing differently, and
`POST /admin/v1/config-revisions/{id}/rebase` merges the live changes in after
you choose `draft` or `live` for every conflicting path. The console's Draft
page does this with both values side by side.

`config promote` starts a draft from another environment's live revision in
the same application. Features, models, input accounting, pricing, limit plans,
session and privacy settings come from the source. The target keeps its own
sign-in providers, attestation policies, component definitions and AI
connections; entries only the source has are copied and listed for review,
because they may point at the source's projects, app identifiers, base URLs or
secret references. Promotion refuses while the target has an unpublished draft.

## Activation safety

Validation covers schema, duplicate keys, references, secrets, identity and
attestation settings, CEL, model capabilities, trusted input accounting,
pricing, route bounds, destination policy, retries, limits, and active user
overrides. Activation fails when the draft is invalid or its strong ETag is
stale. The CLI reports bounded validation issue codes, JSON Pointer paths, and
safe messages without echoing rejected field values.

Rollback atomically reactivates a previously valid revision; it does not edit
history. Configuration activation is audited with actor, target, operation,
and classification metadata, not secret or before/after values.
