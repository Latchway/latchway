# Administration threats

## Bootstrap and identity

The first owner flow requires a high-entropy `LATCHWAY_ADMIN_BOOTSTRAP_TOKEN`, stores only its hash, consumes it transactionally, and permanently closes after an owner exists. A remaining environment variable triggers a warning but cannot reopen bootstrap. Local passwords use Argon2id with versioned parameters. Cookie sessions require secure attributes, CSRF tokens, origin checks, expiry and revocation.

A password an owner sets (on creation or reset) is temporary: until the administrator chooses their own, their session can only read itself, read system status, change the password and sign out. A self-service change verifies the current password under the login failure limiter, refuses reuse, and revokes the administrator's other console sessions in every organization. Ended sessions explain their end reason only to the holder of that session's cookie; unknown cookies get the generic authentication failure. Organization switching re-issues the session for an active membership and revokes the old one atomically. Session records keep a coarse "Browser on OS" summary, never the raw User-Agent or a network address (ADR 0040).

Two-factor sign-in (ADR 0041) uses RFC 6238 TOTP keys sealed under a master-key-derived, administrator-bound key; each code works once. A correct password for a two-factor account yields only a hashed, five-minute, five-attempt challenge, and wrong codes also count against a per-administrator limiter. Recovery codes are hashed and single use. An organization can require a second factor, which confines members without one to enrollment; turning the factor off needs the password and a current code and is refused while required. Owner resets of a member's factor follow the password-reset cross-organization rule.

Passkeys (ADR 0042) are origin-bound WebAuthn credentials verified as ES256 with user presence and user verification required, so a look-alike site can't replay them; they sign in on their own and also satisfy the second factor and the organization requirement. Challenges are random, stored hashed, single use and five minutes long; a second-factor challenge is tied to its password sign-in. A signature counter that fails to advance refuses the assertion as a possible clone. Adding or removing a passkey needs the current password, so a stolen session cookie can't plant a persistent sign-in credential. Attestation isn't evaluated, so the server can't prove a passkey is device-bound; synced passkeys inherit the security of the account that syncs them. Unauthenticated sign-in prompts are capped at 1,000 pending, bounding storage; reaching the cap delays passkey sign-in only. Passkeys need a domain name (or localhost) as the public origin; on an IP address they're unavailable.

Single sign-on (ADR 0043) uses the OpenID Connect authorization code flow with PKCE S256, a random state and nonce, and a browser-binding cookie, so a callback can't be replayed, forged across sites or finished in another browser. ID tokens must be signed with RS256 or ES256 by keys from the issuer's own JWKS and match issuer, audience, expiry and nonce. Provider endpoints are reached only through the public-destination, redirect-free upstream transport, which prevents the configuration from probing internal networks. The client secret is sealed under an organization-bound derived key and never returned. An organization's identity provider is trusted for that organization only: a single sign-on session can't switch organization and isn't held to the Latchway two-factor requirement, which delegates further factors to the provider. Linking by email needs `email_verified` and, when configured, an allowed domain; provisioning never creates owners. Owners keep their password and passkeys when single sign-on is required, so a broken provider can't lock an organization out.

Invitations (ADR 0044) are bearer links: 256-bit tokens stored only as domain-separated hashes, single use, seven days, revocable and replaced by a newer invitation for the same address. The token travels in the URL fragment, so it stays out of server logs and referrers, and the console removes it from the address and history at once. An invitation creates a new account only for an address without one; an existing account must sign in through its normal methods (password plus second factor, passkey or SSO) before it can claim an invitation, and only for its own address, so an invitation link never bypasses an account's protections. Optional email delivery requires TLS to the relay except on localhost, never puts user input in headers, and records failures instead of hiding the link.

Application roles (ADR 0045) only raise a member's role in one application, so an authorization check that doesn't consider them fails closed. Every application-scoped mutation checks the target's own application after loading it; organization-wide actions use the organization role. Roles are read from the database on every request, so removing one takes effect at once. Role preview is display-only in the console and never changes server authorization.

## Authorization

Capabilities derive from server-side memberships and the roles `owner`, `admin`, `operator`, and `viewer`. Every Admin API handler checks the specific capability and tenant scope. UI hiding is not authorization. API tokens are high-entropy, displayed once, hashed, scoped, expirable, revocable, and audited. A bearer-authenticated token creation request may delegate only capabilities in that bearer's effective scope; the administrator's broader underlying role cannot elevate it.

## Configuration and secrets

Draft revisions use ETags to prevent lost updates. Activation validates schema, references, secret availability, CEL compilation, protocol capability, pricing, and route simulation, then changes one active pointer atomically. Rollback activates a prior immutable revision.

Secret create/rotate input is write-only. Responses contain metadata, never plaintext. Authenticated encryption associated data binds organization, environment, secret, version, and format. The environment master key is required only at runtime, never stored in PostgreSQL or logs.

## Audit and privacy

Every administrative mutation records actor, capability, tenant, action, target, result, request ID, timestamp, and a redacted change summary. Audit records exclude passwords, bootstrap/API tokens, provider secrets, identity/refresh tokens, DPoP proofs, raw attestation evidence, and prompt bodies. Access to users, installations, request metadata, and optional prompt bodies is separately authorized and logged.

## Operational attacks

Rate-limit login and token endpoints; detect credential stuffing and session fixation; prevent cross-tenant ID enumeration; enforce secure proxy/host configuration; redact diagnostics; and ensure CLI secrets enter by stdin, file descriptor, or named environment variable rather than command arguments. A newly issued CLI API token goes only to a caller-selected, exclusive mode-`0600` regular file and never to terminal output. Browser copy actions explicitly warn that an operating-system clipboard is outside the console's storage boundary. Backup and restore must preserve encryption metadata and audit integrity without capturing the external master key in the database backup.
